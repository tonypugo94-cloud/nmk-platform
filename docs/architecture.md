# Архитектура

## Принципы

1. **Сервис = модуль = контейнер.** Свой процесс, свой healthcheck, свой перезапуск.
2. **Своя схема и своя роль в БД.** Сервис `svc_<name>` пишет только в свою схему. Чужие данные — через представления `api_*` и функции, на которые выдано право явно.
3. **Общение через события.** `bus.publish()` вызывается в той же транзакции, что и изменение данных. Подписчик забирает доставки `bus.claim()`, подтверждает `bus.ack()`; при ошибке `bus.nack()` — повтор с паузой 5 с → 15 мин, после 8 попыток — `dead` (видно в `bus.api_stats`).
4. **Лежащий сервис ничего не ломает.** Его события копятся и обрабатываются после старта. Внешние системы (1С, МетеоПлан, мессенджеры) вызываются через `CircuitBreaker`.
5. **Реестр модулей.** Сервис при старте регистрирует манифест в `core.app_modules` (название, меню, роли, зависимости) и шлёт heartbeat. Включает модуль администратор. Интерфейс строит меню из включённых модулей.
6. **База — единая точка отказа**, осознанно. Компенсация: бэкапы, архивация WAL, проверенное восстановление, мониторинг. Цели: RPO ≤ 15 мин, RTO ≤ 2 ч.

## Ядро (`core`)

Роли пользователей (данными, модули добавляют свои), профили, реестр модулей, настройки, справочники (направления, кладбища с координатами, машины, бригады, стадии), клиенты (минимум ПДн + обезличивание по сроку), номенклатура, заказы, журнал заказа (`core.order_events` — копия всех событий с ключом `order:<id>`, хранится всегда).

Стадия заказа приходит из реквизита «Стадия производства» в 1С. Ручная смена стадии и будущие сканы QR не откатываются, если в 1С поменяли другое поле: стадия из 1С применяется, только когда в 1С поменялось именно её значение.

## Как добавить новый модуль (в том числе не из исходного плана)

1. Миграция `supabase/migrations/NNNN_<module>.sql`: своя схема, `select core.ensure_service_role('svc_<name>')`, права роли только на свою схему и нужные `api_*`, при необходимости — роли пользователей в `core.roles` с `module_key`.
2. События — в каталоге (`defineEvent`), с Zod-схемой.
3. Сервис `services/<name>/src/main.ts` через `runService({ name, module, subscriptions, tasks })`.
4. Контейнер в `infra/docker-compose.yml` по шаблону `x-service`, пароль роли в `.env`.
5. Тесты: логика + сценарий «сервис лежал — события догнались».
6. Администратор включает модуль — он появляется в меню.

Ядро при этом не меняется.
